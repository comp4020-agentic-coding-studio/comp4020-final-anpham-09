# Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make identity the person rather than the browser, so that one human signed in on two devices is one person everywhere the app records who did something.

**Architecture:** The cookie stays a session. A stable `person_id` becomes identity — `m:<account name>` for a member, `v:<cookie token>` for a visitor — and is written into the columns that currently hold raw tokens. No schema change: those columns are already bare `TEXT` with no foreign keys. The `keepings_not_own` trigger and the games `CHECK (top != bottom)` then compare people instead of browsers, so both fixes land in the schema rather than in new checks.

**Tech Stack:** Node 24 running TypeScript directly (no build step, `.ts` import extensions), `better-sqlite3`, Vitest. `pnpm check` = `tsc --noEmit` + `vitest run`.

/** Who a request acts as. The cookie is a session; this is the person.
 *
 *  A member is the same person on every device they sign in on, which is
 *  what makes the shelf rule and the game's two chairs true of humans
 *  rather than of browsers. A visitor is still their own browser, which is
 *  the honest answer for somebody who has not said who they are: two
 *  strangers who both typed "Linh" are not one person.
 *
 *  The prefixes matter. Without them a visitor whose cookie happened to read
 *  "Mum" would be the member Mum, and a bare value could not be told apart
 *  from a row written before accounts existed. */
export function personId(person: Person | undefined, token: string): string {
  return person?.memberName ? `m:${person.memberName}` : `v:${token}`;
}

/** The name to show for a person id, from either kind. An id with no
 *  prefix is a row written before accounts existed and is read as a
 *  visitor, so an un-migrated database shows names rather than ids. */
export function nameForPersonId(id: string): string {
  if (id.startsWith("m:")) return id.slice(2);
  const token = id.startsWith("v:") ? id.slice(2) : id;
  return getPerson(token)?.name ?? "someone";
}

/** What to call somebody on their own screen. A member is their account
 *  name: the key says who you are, so the page must not call you something
 *  else on the strength of a text box. */
export function displayName(person: Person | undefined): string {
  return person?.memberName ?? person?.name ?? "someone";
}
```

/** Identity used to be the cookie token, written bare into these columns.
 *  It is now a person id. Rows written before that change are visitors by
 *  definition — nobody had an account yet — so they take the "v:" prefix.
 *
 *  Idempotent, because it only touches a value carrying neither prefix, and
 *  safe for `keepings`, whose UNIQUE (thing_id, person) survives a rewrite
 *  that is the same for every row. No row is deleted and no column is
 *  dropped: the only thing that changes is how an identity is spelled. */
const IDENTITY_COLUMNS: ReadonlyArray<readonly [table: string, column: string]> = [
  ["things", "placed_by"],
  ["perspectives", "author"],
  ["keepings", "person"],
  ["presence", "person"],
  ["games", "bottom"],
  ["games", "top"],
];

export function migrateIdentities(): void {
  for (const [table, column] of IDENTITY_COLUMNS) {
    // Table and column names are literals from the list above, never input.
    db.exec(
      `UPDATE ${table} SET ${column} = 'v:' || ${column}
        WHERE ${column} IS NOT NULL
          AND ${column} NOT LIKE 'v:%'
          AND ${column} NOT LIKE 'm:%'`,
    );
  }
}

migrateIdentities();
```

## Known limitation, carried from the spec

Somebody who acts as a visitor and *then* signs in keeps their earlier content
under `v:<token>` while becoming `m:<name>`, and could keep their own earlier
thing. Reclaiming it means rewriting four tables and resolving
`UNIQUE (thing_id, person)` collisions, and every resolution would drop a
keeping, which the app may not do. Out of scope; the window is small because
production starts empty and the five sign in before using it.

A second, smaller one: signing in changes your person id mid-session, so the
presence row written as `v:<token>` lingers until the 45-second TTL expires.
The effect is that you briefly appear twice in a room. Not worth a migration.

## Trade-off worth stating

`m:<account name>` makes the name the primary key of a person. Renaming an
account orphans everything that person placed. The five names are fixed in
`MEMBER_KEYS` and were chosen by the family, so this is acceptable now; if a
name ever has to change, it needs a migration that rewrites the same six
columns, not an edit to the secret.
